# Decks table interaction contract

Status: initial contract, 2026-09-21.

The owner-only hand tray renders cards in the server-provided private hand order, with accessible earlier/later controls that submit the complete hand order as `reorder_hand`. A player can select cards from only their own hand, choose an active host/player recipient, and either give the selection privately or return it to its source decks top/bottom. Give and return requests carry exact expected versions for every selected card. The recipient control uses safe generic participant labels and counts; it never displays account email or raw participant IDs. The hand order and card identities are excluded from every other participant's projection and public event.

When the actor has both `card.manage` and `pile.manage`, the hand-selection toolbar also lets them move selected own-hand cards into a selected unlocked pile. The action carries an exact expected-card-version map and the destination pile version; it validates the complete hand selection, ownership, locks and target before changing state atomically. The cards become face down in the pile, leave the source hand, and are not identified in public activity or other participants' projections. Pile choices use safe labels and counts.

The first client uses ordinary DOM elements inside a transformable table. Pointer Events drive local drag previews; pointer release submits one durable action. Every essential drag operation has an action-menu alternative. Pan/zoom, selection, rotation, z-order, keyboard focus, touch-sized controls and reduced motion are presentation concerns; final position and containment are server state.

Create-table responses display an opaque join token for authenticated players. The Join table control submits that token unchanged to the token-only join endpoint; it never assumes the token is encoded JSON or decodes its segments in the browser.

Table cards support public face-up, public face-down and private hand projection. A hand exposes identities only to its owner. Public overlap never silently creates a pile; stacking is an explicit action. Visible cards use safe display names where authorized, while hidden projections use generic labels. Cards are keyboard-focusable and provide explicit action alternatives to drag or double-click. Pending actions and rejected conflicts remain visually distinct from accepted state.

The table viewport provides local Zoom out, Zoom in and Reset zoom controls with a bounded 50%–150% scale. The current scale is announced accessibly. The tabletop can be panned with its native horizontal/vertical scrolling, trackpad and touch scrolling; card and pile drags remain object moves and are not repurposed as viewport pan. Zoom is presentation-only: the browser scales the board and converts pointer deltas back to logical board coordinates before submitting a card/pile move. It does not send zoom, viewport offsets or scaled positions as durable session state. Zoom and scroll position remain stable while the current session snapshot refreshes. Acceptance checks the minimum/maximum controls, centered zoom behavior, scrolling at narrow widths, card/pile movement at non-default zoom, and keyboard operation without changing the action request's coordinate semantics.

The initial operation family is shuffle, draw top/bottom/N, move table card, rotate, flip/turn face, move to own hand, play from own hand face-up/down and return selected cards to deck top/bottom. The current pile slice adds create, move a validated selection into a pile, shuffle a pile and merge a pile into a deck top/bottom. S18 adds pile draw top/bottom, split/merge pile-to-pile, collect-spread, pile spatial/label/lock operations, group table-card rotation/reveal/z-order, and their version checks. All selection members are validated before mutation; hidden hands and removed cards remain inaccessible. Group selection state stays in the browser while final results are durable server state.

The selection toolbar provides “Return selection to source decks top” and “Return selection to source decks bottom” for the current table selection the actor can see and control. The server resolves each card's source deck, so clients do not receive or submit source-deck associations. Buttons are disabled until one or more eligible table cards are selected. The request carries the selected card ids and exact expected card-version map; the service validates all versions, locations, visibility, locks, and the actor's `card.manage` and `deck.manage` capabilities atomically. Selection order determines each source deck's returned group order. This control does not reveal card identity or source-deck association and the durable public event omits card ids.

The selection toolbar offers “Remove selected card from play” only when exactly one visible public table card is selected. It confirms the user's choice, submits that card id and exact version to the existing `remove_card` action, and lets the service enforce capability and lock checks. Removal hides the card from ordinary table/deck/pile projections. During a mutable session, a host with effective `card.manage` receives a recovery list containing only opaque removed-card ids and versions needed for the existing `restore_card` action. The UI labels every entry generically and offers source-deck restoration at top, bottom, or server-randomized position; it never presents the card definition/name, protected asset path, source-deck association, or removed-card ordering. No other participant receives this recovery projection. Removal/restoration events and recent history remain sanitized; ended sessions expose no mutation control.

For each unlocked, nonempty pile, participants with both `pile.manage` and `deck.manage` can choose a session deck by safe label and count and merge the pile onto its top or bottom, or shuffle it into the deck. Each operation submits the observed pile and deck versions. The controls expose no contained card identities or resulting order; shuffle-in is server-randomized.
